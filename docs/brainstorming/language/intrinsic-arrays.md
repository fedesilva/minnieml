# Intrinsic arrays

Status: Draft
Ticket: `#202` (`https://github.com/fedesilva/minnieml/issues/202`)

---

## Goal

Give MML a single array type that works for any element type.

Today the language has three separate array types, one per element type, each with
its own set of functions. This design replaces them with one `Array` type and one set
of operations.

This is a deliberate middle step. A general polymorphic type system is not in place
yet. Instead, `Array` is a built-in type that takes an element type as a parameter,
and the compiler produces a concrete version of each array operation for every element
type it encounters. The runtime representation stays the one in use today; it is just
moved behind a type constructor with proper syntax for indexed access. The result
behaves like a polymorphic array without requiring the full polymorphic type system.
That system can come later; this design is meant to survive it.

---

## Scope

In scope:
- `Array` as a built-in type, written `Array Int`, `Array Float`, `Array String`, and
  so on.
- Array literals: `[1, 2, 3]`.
- Sized construction, element access, and length.
- Type checking for array types and array literals.
- Code generation for all of the above.
- Memory handling: arrays own their storage and are freed and cloned correctly,
  including when the element type owns heap memory.

Not in scope:
- User-written functions that are generic over the element type. Code can use
  `Array Int` or `Array String` directly — as values, parameters, and struct fields —
  but cannot yet write one function that works for any element type. That waits for
  the polymorphic type system.
- User-defined generic types.
- Optimizer work beyond straightforward literal construction.

---

## What this replaces

The standard library currently provides three array types — `IntArray`,
`StringArray`, `FloatArray` — each a heap struct of a length and a data pointer. It
also provides a separate construction, element access, length, free, and clone
function for each, and the unchecked accessors exist only for some element types.

This design removes all of that:
- The three types in `prelude.mml` become one `Array` type.
- The per-type functions in `prelude.mml`, and their implementations in
  `mml_runtime.c`, are removed. Element access and length become code the compiler
  emits directly. Sized construction keeps one small runtime helper. Free and clone
  are generated by the compiler, one pair per element type.

## The array type

### One type constructor

`Array` is a built-in type that takes exactly one type argument: the element type.

```mml
let xs: Array Int = [1, 2, 3];
let ys: Array Float = [1.0, 2.0, 3.0];
let zs: Array (Array Int) = [[1, 2], [3, 4]];
```

`Array` on its own is not a type; it must be applied to an element type. Applying it
to zero or more than one argument is an error.

### Element type matching

`Array A` and `Array B` are the same type only when `A` and `B` are the same type.
There is no widening between array types: an `Array Int` is never accepted where an
`Array Float` is expected, and the other way around.

### Arrays in other positions

An array type can be used anywhere a type can: variable bindings, function parameters
and results, and struct fields.

```mml
struct Grid { width: Int, height: Int, cells: Array Int };

fn row_sum(xs: Array Int): Int = ... ;
```

### Mutability

Arrays are mutable. `set` writes a slot in place. The length is fixed when the array
is created.

## Surface syntax

### Type syntax

An array type is written by juxtaposition, the element type following `Array`:
- `Array Int`
- `Array String`
- `Array (Array Int)` — parentheses group a nested array type.

### Literal syntax

An array literal is a comma-separated list of elements in square brackets:
- `[1, 2, 3]`
- `["a", "b"]`
- `[]`

All elements must have the same type. That type becomes the element type of the array.

### Empty literal

`[]` has no elements to take a type from, so its element type must come from context —
an ascription, or the expected type at its use site:

```mml
let xs: Array Int = [];
```

An `[]` with no such context is a compile error. The compiler does not guess an
element type.

## Operations

Names below are provisional; final names are an open question (see the end of this
document).

### Construction

`array_new n init` creates an array of `n` elements, every slot set to `init`:

```mml
let xs = array_new 100 0;     // Array Int, 100 zeros
let ys = array_new 100 0.0;   // Array Float
```

`init` is required. It gives every slot a valid starting value. This matters when the
element type owns heap memory: an array of strings created this way holds `n` valid
strings, not uninitialized memory. When the element type owns heap memory, each slot
gets its own copy of `init`.

### Element access

- `array_get arr i` returns the element at index `i`.
- `array_set arr i v` writes `v` into slot `i`.

Both check that `i` is within bounds. An out-of-bounds index stops the program with an
error. This matches what the current checked accessors do.

### Unchecked element access

- `array_unsafe_get arr i`
- `array_unsafe_set arr i v`

The same as the checked forms, with no bounds check. They exist for hot loops where
the index is already known to be valid; an out-of-bounds index here is undefined
behavior. The performance-sensitive sample programs depend on these, so they are
included from the start.

### Length

The length is a field of the array. Read it directly:

```mml
let n = xs.length;
```

## How it is built

### Type AST

The type AST already has a `TypeApplication` node (a base type applied to type
arguments). `Array Int` is that node, `Array` applied to `Int`. The work is to
register `Array` as a built-in type constructor that takes exactly one argument; no
new type node is needed.

### Term AST

A new term node is needed for the array literal: one holding the list of element
expressions. There is no equivalent node today.

### Parser

- In type position, parse `Array <type>` as the applied type.
- In term position, parse `[ e1, e2, ... ]` as an array literal.

### Type checking

- An array type resolves through `Array` as a built-in constructor with exactly one
  argument.
- For a non-empty literal: infer each element's type, check they all agree, and give
  the literal the type `Array <element>`.
- For `[]`: take the element type from the ascription or the expected type; with
  neither, report a dedicated error.
- Report a clear error for mixed element types in a literal, and for `Array` applied
  to the wrong number of arguments.

### Code generation

An array value is a length and a data pointer — the same shape as `String`. The
element type tells code generation the size and layout of each slot.

- Element access, checked and unchecked, is emitted directly as address arithmetic
  plus a load or store, with a bounds check for the checked forms. No runtime function
  call.
- `array_new` calls one small runtime helper to allocate storage, then fills the slots
  with `init`.
- An array literal allocates storage and fills it. When the elements are constants and
  the element type does not own heap memory, this can be a single copy of a constant
  block; otherwise it is one store per element.
- The compiler produces a concrete version of each operation for every element type it
  sees, and reuses it when the same element type appears again.

### Memory and ownership

An array owns its storage. It is a heap value and follows the same ownership rules as
other heap values such as `String`.

Free and clone are generated by the compiler, one pair per element type, the same way
memory helpers are already generated for structs with heap fields:
- When the element type does not own heap memory (such as `Int` or `Float`), freeing
  an array releases its storage, and cloning copies the storage directly.
- When the element type itself owns heap memory (such as `String`, or a struct with
  heap fields), freeing an array first frees each element, and cloning makes a deep
  copy of each element.

`array_new` and `set` take ownership of the values they store when the element type
owns heap memory.

## Migration

1. Add `Array` and the array literal; keep the existing array types in place.
2. Move the sample programs and tests over to `Array`.
3. Remove `IntArray`, `StringArray`, `FloatArray` and their functions from
   `prelude.mml`, and the matching code from `mml_runtime.c`.

Intermediate breakage between these steps is fine.

---

## Implementation order

1. Type AST and parser: the `Array` type and the array literal.
2. Type checking: array types, literal typing, the empty-literal error.
3. Code generation for an element type that does not own heap memory first
   (`Array Int`), then any element type.
4. Memory handling: generated free and clone, ownership integration.
5. Construction and access operations.
6. Tests at each step; migrate the samples last.

---

## Open questions

1. Final names for the operations (`array_new`, `array_get`, and the rest).
2. Whether to also allow a one-argument `array_new n` for element types that have a
   natural zero, as a shorthand.
3. What happens to the previous occupant of a slot when `set` overwrites it, for an
   element type that owns heap memory.
4. Whether constant array literals get the single-copy optimization in the first
   version or a later one.
